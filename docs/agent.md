# AI-агент Jarvis (Stage 3)

Jarvis — не командный бот с меню, а ассистент: пользователь пишет естественно
(«Джарвис, какие задачи по проекту SuperSport ещё не закрыты?»), а агент сам
вызывает типизированные инструменты, получает реальные данные и собирает ответ
или интерактивный UI. Всё, что показывает агент, приходит из БД приложения —
модель не выдумывает сущности.

## Архитектура

```
Telegram update
  │
  ▼
bot/handlers/free_text.py ──► conversation/engine.py  (роутинг)
                                  │  обращение по имени / продолжение
                                  │  агентского контекста / intent=unknown
                                  ▼
                        agent/orchestrator.AgentService
                          ├─ agent/routing      профиль и детект «Джарвис»
                          ├─ agent/queue        per-user очередь + отмена
                          ├─ agent/budget       дедлайн, шаги, токены, циклы
                          ├─ agent/prompts      системный промпт + контекст
                          ├─ AIProvider.plan()  LLM (OpenCode Go / fake / none)
                          └─ agent/tools        типизированный реестр инструментов
                                  │
                                  ├─ TaskService / репозитории (задачи, проекты, знания)
                                  ├─ ConfirmationService (высокий риск → кнопка)
                                  ├─ ImprovementService (пробелы → backlog)
                                  └─ research/ (web_search: none | fake)
```

Бизнес-логика не дублируется: инструменты вызывают те же сервисы и
репозитории, что и обычные сценарии бота.

## Роутинг и приоритеты

`conversation/engine.handle_text` решает, кто обрабатывает сообщение:

1. Активные пошаговые сценарии (ожидание значения секрета, файла, правки
   комментария и т.п.) — обрабатываются выше агента и не сбиваются.
2. Явное обращение по имени — **«Jarvis»/«Джарвис»** (регистронезависимо,
   отдельный токен; внутри слов и через дефис не срабатывает) — всегда агент.
   Упоминание **«бэклог/backlog/диагностик»** тоже всегда уходит агенту:
   «выведи бэклог» и «запиши в бэклог ...» не должны превращаться в задачи
   и заметки.
3. Продолжение агентского контекста (`conversation_states.flow = agent_context`) —
   агент, пока контекст не истёк (TTL `CONVERSATION_STATE_TTL_HOURS`, 24 ч).
4. Эвристики («найди ...») и обычная интерпретация — как раньше.
5. `intent = unknown` больше не тупик: подключается агент.

Обращение по имени имеет приоритет над эвристиками и fallback'ами, но не
обходит авторизацию, бюджеты, подтверждения и отмену.

## Инструменты (allow-list)

Реестр — `src/jarvis/agent/tools.py`. У каждого инструмента: pydantic-схема
аргументов (уходит в промпт), признак мутации и уровень риска, структурированный
результат `{"ok": true, "data": ...}` / `{"ok": false, "error": {"kind", "message"}}`.

| Инструмент | Тип | Риск | Назначение |
|---|---|---|---|
| `list_tasks` | read | low | списки (today/week/…/done + `all` — все незавершённые), на дату (`on_date`), по категории (`category`) |
| `list_project_tasks` | read | low | незавершённые задачи проекта по названию |
| `search_tasks` | read | low | FTS + подстрочный поиск задач |
| `get_task` | read | low | карточка задачи + последние комментарии |
| `search_all` | read | low | знания + задачи + документы |
| `get_knowledge` | read | low | полный текст записи знаний (в т.ч. чувствительных) |
| `send_document` | read | low | файл документа вложением в чат (расшифровка на время отправки) |
| `list_projects` | read | low | проекты (id/названия) |
| `create_task` | mutation | low | превью + кнопка: задача создаётся после подтверждения |
| `create_category` | mutation | low | превью + кнопка; идемпотентно (уже есть / уже предложена) |
| `rename_category` | mutation | low | превью + кнопка: переименование категории-папки |
| `update_task` | mutation | low | превью + кнопка: статус/приоритет/группа/срок/заголовок/проект (проект создаётся, если его нет; `project=«нет»` — убрать); `due_at=null` — убрать срок |
| `add_comment` | mutation | low | превью + кнопка: комментарий к задаче |
| `update_comment` | mutation | low | превью + кнопка: правка текста комментария (id из get_task) |
| `delete_task` | mutation | **high** | только отправляет pending-подтверждение |
| `delete_knowledge` | mutation | **high** | только отправляет pending-подтверждение (удаление заметки) |
| `delete_document` | mutation | **high** | только отправляет pending-подтверждение (удаление документа) |
| `create_knowledge` | mutation | medium | превью + кнопка: заметка (sensitive=true для кредов) |
| `update_knowledge` | mutation | medium | превью + кнопка: правка заметки (заголовок/сводка/текст/категория/проект/чувствительность), работает и с sensitive |
| `update_document` | mutation | medium | превью + кнопка: название, категория-папка и/или чувствительность документа |
| `web_search` | read | low | внешний поиск (Tavily; источники указываются в ответе) |
| `report_capability_gap` | mutation | low | запись пробела в improvement backlog |
| `list_improvements` | read | low | чтение backlog (для «покажи бэклог») |
| `daily_stats` | read | low | дневная статистика: действия по типам, закрытые задачи, новые записи backlog (date — по умолчанию сегодня) |
| `update_improvement` | mutation | medium | смена статуса записи backlog (как в /diagnostics; применяется сразу, без кнопки) |
| `export_chat` | read | low | журнал диалога за день (MD + JSON) файлами в чат |
| `export_issues` | read | low | improvement backlog (диагностика) файлами MD + JSON в чат |

Файлы, подготовленные `send_document`/`export_chat`/`export_issues`, уходят в чат
вложениями сразу после текста ответа (поле `files` результата агента →
`EngineOutcome`).

Экраны (`ui = {"component": "screen", ...}`) — allow-list в
`AgentService._validate_screen`: `tasks` (view= today/week/month/long_term/
someday/no_group/inbox/all/done, либо on_date, либо category), `search`
(query), `documents` (category), `knowledge` (последние записи), `card`
(kind=task|knowledge|document + id). Сервер строит настоящие списки и карточки
с живыми кнопками действий; параметры валидируются, неизвестные экраны
отбрасываются. Списки задач, документов и знаний — по 7 на страницу со стрелками
«⬅️/➡️» (как в классических `/tasks`, `/documents`, меню «Знания»).

### Покрытие интерфейса (аудит кнопок, 17.10)

Проверено, что каждая кнопка/место бота достижимы агентом (кроме секретов —
исключены решением владельца):

| Место UI | Кнопки | Чем закрывает агент |
|---|---|---|
| Главное меню | 🔎 Поиск, ✅ Задачи, 📚 Знания, 📄 Документы, 🗂 Проекты, ⚙️ Настройки | экраны `search`/`tasks`/`knowledge`/`documents`, `list_projects`+`create_project`, `create_category`+`rename_category` |
| Меню «Задачи» | Сегодня, На этой неделе, В этом месяце, Все задачи, Без срока, Выполненные, По категориям | экран `tasks` (`view`, `category`); `on_date` — для «задачи на 19 октября» |
| Карточка задачи | изменить срок, группа, завершить/вернуть, комментарии (список/добавить/править), удалить, к спискам | `update_task` (срок/группа/статус/проект), экран `card`, `list_comments`+`add_comment`+`update_comment`, `delete_task` |
| Знания | список, карточка, полный текст, похожие, удалить | экран `knowledge`, экран `card`, `get_knowledge`, `search_all`, `delete_knowledge` |
| Документы | список, по категориям, карточка, получить файл, категория, удалить | экраны `documents`/`card`, `send_document`, `update_document`, `delete_document` |
| Проекты | список, новый проект | `list_projects`, `create_project` (редактирования проектов нет и в UI) |
| Настройки | категории: новая/переименовать | `create_category`, `rename_category` |
| Диагностика | backlog, статусы, экспорт, удаление записи | `list_improvements`, `update_improvement`, `export_issues`; экран открывается quick action «🩺 Диагностика». Удаление записей — только в `/diagnostics` (необратимо) |
| Экспорты | `/export_chat`, `/export_issues` | `export_chat`, `export_issues` |
| Секреты | все | исключены владельцем (значения не должны проходить через LLM) |

Ошибки различаются по видам: `validation`, `not_found`, `unsupported`,
`transient` (единственный вид, который повторяется — до
`AGENT_MAX_TOOL_RETRIES`), `internal` (детали не утекают в LLM, только в логи).

Высокий риск (`delete_task`, `delete_knowledge`, `delete_document`) и правки
(`create_knowledge`, `update_knowledge`, `update_document`, `update_improvement`)
не применяются сразу: создаётся pending-операция Stage 1, пользователю приходит
превью с кнопкой «Подтвердить / Изменить / Отменить»; подтверждение привязано к
пользователю и истекает по TTL. Если за один запрос предложено несколько
операций — у каждой свои превью и кнопки (ни одна не теряется).

Тексты, которые агент сохраняет (задачи, заметки, комментарии, записи бэклога),
он слегка вычитывает: опечатки, повторы и ошибки распознавания голоса. Смысл,
имена, термины, числа, даты, ссылки и цитаты не меняются; исправленный вариант
виден в превью, «Изменить» остаётся страховкой.

## Агентский цикл

Каждый шаг — один JSON от LLM (`PlanStep`):

```json
{"type": "tool_call", "tool": "list_tasks", "args": {"view": "no_group"}}
{"type": "reply", "text": "…", "ui": null}
```

Оркестратор (`agent/orchestrator.py`): проверяет бюджет → спрашивает план →
валидирует и выполняет инструмент → добавляет результат в историю → повторяет.
Завершение: `reply`, лимит бюджета (частичный итог), отмена, ошибка LLM.

Интерфейс `AIProvider.plan()` поддерживают те же провайдеры, что и раньше
(OpenCode Go — structured output с ремонтным повтором; fake — для тестов;
none — агент выключен, система работает как раньше).

## Контекст и разрешение сущностей

- После каждого запроса в `conversation_states.data` сохраняются:
  `agent_candidates` (реальные сущности, которые агент показывал/находил) и
  `agent_last_run` (метрики запроса).
- Промпт следующего запроса получает выбранную сущность (`agent_selected`) и
  пронумерованных кандидатов — поэтому «добавь к первой комментарий» работает
  без повторения названия.
- Кнопки `entity_choice` содержат только серверный индекс; id и заголовки
  берутся из контекста и перечитываются из БД в момент нажатия. Исчезнувшая
  сущность → честное «больше недоступна», кандидат убирается.
- `entity_choice` из ответа LLM принимается, только если все id есть среди
  реально показанных в этом запросе (иначе UI отбрасывается и это пишется в лог).

## UI-описания

Модель может добавить к финальному ответу `ui`:

- `quick_actions` — кнопки строго из allow-list (`bot/keyboards.UI_ACTION_BUTTONS`);
- `entity_choice` — выбор реальной сущности (проверяется сервером, см. выше).

Допустимы только эти компоненты (валидирует Pydantic-дискримированное
объединение `AgentUI`). Произвольные callback'и, разметка или действия модель
сформировать не может — callback'и всегда строит сервер.

## Бюджеты, отмена, очередь

Центральный контроллер — `agent/budget.ExecutionBudget` (общий на весь запрос,
дедлайн по `time.monotonic()`, не сбрасывается вызовами инструментов):

| Лимит | ordinary | planning | research | Настройка |
|---|---|---|---|---|
| время | 60 c | 120 c | 300 c | `AGENT_*_SECONDS` |
| шаги | 12 | 20 | 40 | `AGENT_*_STEPS` |
| web-запросы | 1 | 3 | 8 | `AGENT_WEB_QUERIES_*` |

Общие: `AGENT_MAX_LLM_CALLS` (18), `AGENT_MAX_REPEAT_TOOL_CALLS` (2 — одинаковый
вызов с теми же аргументами), серия из 4 ошибок подряд, `AGENT_MAX_TOOL_RETRIES`
(1, только для `transient`), токены `AGENT_TOKEN_SOFT_LIMIT`/`HARD_LIMIT`
(по умолчанию 50 000 / 150 000; действуют **только** если провайдер отдал `usage`;
иначе лимиты по времени и шагам — и это честно видно в диагностике:
`tokens=null`).

При исчерпании бюджета: новые шаги не запускаются, летящий план прерывается по
дедлайну (`asyncio.wait_for`), выполняется один финальный проход без инструментов
(«что известно / что осталось»), при невозможности — шаблонный частичный итог.
Незавершённое никогда не выдаётся за готовое.

Отмена: `/cancel` выставляет флаг текущему запросу пользователя
(`agent/queue.UserSessionGate`). Проверки — перед каждым шагом и сразу после
возврата плана: поздний ответ модели после отмены не применяется. Новые
мутации после отмены не запускаются; уже начатый инструмент завершается (локальная
отмена не отменяет HTTP-запрос провайдера — состояние фиксируется честно).

Очередь: агентские запросы одного пользователя сериализуются `asyncio.Lock`
(ожидание до `AGENT_QUEUE_WAIT_SECONDS`, потом «занят»). Зависший запрос
освобождает очередь по дедлайну. Ограничение: очередь процесс-local; при
запуске нескольких воркеров сериализацию нужно поднимать в PostgreSQL
(advisory-lock) — текущее развёртывание однопроцессное.

## Web-поиск

`research/` — провайдер-независимый интерфейс `WebSearchProvider`
(`search(query, limit) -> [WebSearchResult(title, url, snippet)]`):

- `WEB_SEARCH_PROVIDER=none` — инструмент честно отвечает `unsupported`;
- `fake` — скриптованные ответы для тестов;
- `tavily` — реальный поиск через api.tavily.com (ключ `TAVILY_API_KEY`,
  бесплатный тир 1000 кредитов/мес; подключён в текущем развёртывании).

Инструкции агенту: искать в интернете только когда нужны внешние факты,
никогда не включать в запрос личные данные (содержимое заметок и документов,
секреты, имена сущностей), а в ответе указывать источники (url).

## Связь с improvement backlog

Если запрос объективно невозможен из-за отсутствующей у Jarvis возможности,
агент вызывает `report_capability_gap` → `ImprovementService.record_gap`
(источник `user_observation`, категория `missing_capability`, дедуп по
заголовку). Сообщения «запиши/добавь в бэклог ...» — это пожелание к Jarvis, а не
задача пользователя: правило роутинга уводит их агенту, а промпт запрещает
создавать по ним задачи и заметки. Обычные ошибки пользователя, пустые поиски и
сетевые сбои туда не пишутся (правило в промпте). Разбор backlog — по-прежнему
вручную: `/diagnostics` → `/export_issues` → OpenCode (цикл в `AGENTS.md`).

## Наблюдаемость

- Лог: `agent request done user=… profile=… termination=… steps=… tools=…
  llm=… tokens=… ms=…` (без содержимого запросов; correlation id — из middleware).
- `/diagnostics` показывает строку «AI-агент (последний запрос): …» —
  termination, профиль, шаги, инструменты, токены (если были), длительность.
- Машинные причины остановки: `completed`, `timeout`, `step_limit`, `llm_limit`,
  `token_limit`, `web_limit`, `loop_detected`, `error_streak`, `cancelled`,
  `queue_timeout`, `unavailable`, `ai_error`.

## Тесты

```sh
python -m pytest          # всё (нужен PostgreSQL из compose)
python -m pytest tests/unit
```

Покрыто: роутинг и регистр обращения по имени; приоритет над поиском (e2e);
валидация схем и UI; бюджеты (дедлайн, шаги, локи, токены, отсутствие usage);
очередь и отмена (включая `/cancel` во время выполнения); инструменты
(валидация, not_found, мутации через сервисы, подтверждение удаления,
web-поиск, backlog-пробел); агентский цикл (инструменты, entity_choice,
частичные результаты, повторы).

## Ограничения

- Планировщик — не OpenAI tool-calling, а структурированный JSON
  (`PlanStep`); при неверном выводе один ремонтный повтор, затем ошибка.
- Очередь и отмена процесс-local (см. выше).
- Параллельные read-инструменты внутри запроса не запускаются: выгоды нет,
  бюджет проще (последовательная модель).
- Агент не создаёт секреты и документы: секреты — через /secret, документы —
  вложением файла; категории задач/документов создаются инструментом
  `create_category` или в /settings.
- Агент не удаляет заметки: удаление записи знаний — кнопкой в карточке
  (/knowledge); у агента есть только правка (`update_knowledge`).
