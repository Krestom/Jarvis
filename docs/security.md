# Безопасность Jarvis

## 1. Модель угроз

Система — персональный бот для одного владельца (или узкого круга). Защищаем:

- **знания** — заметки, решения, контекст проектов (могут содержать персональные данные);
- **документы** — файлы (паспорт, договоры, финансы), на диске только в зашифрованном виде;
- **секреты** — пароли, токены, SSH-ключи; отдельное шифрование и полная изоляция от поиска/AI/MCP;
- **ключи и токены** — мастер-ключи шифрования, токен Telegram-бота, `MCP_AUTH_TOKEN`.

Основные сценарии атакующего:

| Атакующий | Вектор | Контрмера |
|---|---|---|
| Посторонний, узнавший бота | Пишет боту от своего Telegram-аккаунта | Allow-list по user id (`src/jarvis/security/auth.py`), событие молча игнорируется |
| Посторонний | Пересылает чужое сообщение / жмёт чужую callback-кнопку | Callback-кнопки не являются доказательством авторизации: проверка allow-list стоит и на callback_query, а подтверждение операции выполняется только для владельца операции |
| Утечка токена бота / .env | Чтение чатов, отправка от имени бота | Токен и .env не в git и не в образе; при утечке — перевыпуск токена у @BotFather и ротация ключей |
| Компрометация VPS | Доступ к процессу, env, томам, БД | Файлы на диске зашифрованы; ключ живёт только в env процесса — при компрометации хоста это остаточный риск (см. раздел 10) |
| Вредоносный контент | Prompt injection в заметке/документе/имени файла | LLM не выполняет операции и не имеет инструментов; в промпте явно сказано, что контент — данные, а не инструкции (`src/jarvis/ai/prompts.py`, правило 8); все изменения — через backend и подтверждение |
| Скомпрометированный Telegram-аккаунт владельца | Полный доступ к боту от его имени | Технически не отличается от владельца — внешняя мера: 2FA Telegram, ограничение устройств |

## 2. Авторизация

- Единственный механизм доступа — allow-list Telegram user id
  (`Authorizer`, `src/jarvis/security/auth.py`).
- **Пустой allow-list запрещает всем**: «отсутствие настройки никогда не
  означает „разрешить всем“». В `prod` пустой allow-list — ошибка конфигурации:
  при заданном токене приложение завершается, не запуская бота
  (`Settings.bot_config_problems`, `refusing to start`); в `dev` с заданным
  токеном — предупреждение.
- Проверка стоит на всех точках входа: `AccessMiddleware` на `message` и
  `callback_query` (`src/jarvis/bot/middlewares.py`). Неавторизованные события
  молча игнорируются — бот не подтверждает, что у него есть база.
- **Callback-кнопки не считаются доказательством авторизации.** Мало того, что
  на них действует тот же allow-list: подтверждение операции дополнительно
  проверяет принадлежность операции — `PendingOperationRepository.resolve`
  ищет операцию по `(id, telegram_user_id)`, и чужой id возвращает
  «не найдена» (`src/jarvis/repositories/pending.py`). Пользователь берётся из
  `callback.from_user.id`, а не из данных кнопки.
- Уборка файловыми хендлерами и голосом идёт через те же роутеры, т.е. после
  middleware-проверки.

## 3. Подтверждения (pending-операции)

- Значимые изменения не применяются напрямую: движок создаёт
  `PendingOperation` (`src/jarvis/services/confirmation.py`) с TTL
  `PENDING_OPERATION_TTL_MINUTES` (по умолчанию 30 минут), пользователь видит
  превью и жмёт «Применить / Изменить / Отменить».
- **Атомарный переход статуса**: `UPDATE pending_operations SET status=… WHERE id=… AND status='pending'`
  (`repositories/pending.py`). Если строка не обновилась — операция уже
  разрешена: повторное нажатие не применяет изменение второй раз (идемпотентность),
  повторный apply возвращает «уже применено», повторный cancel — «уже завершена».
- **TTL проверяется на переходе**: даже если фоновая уборка ещё не пометила
  операцию просроченной, confirm после `expires_at` переводит её в `expired` и
  не применяет.
- **Принадлежность**: операция привязана к `telegram_user_id`; подтвердить или
  отменить её может только этот же пользователь (см. раздел 2).
- **Payload не является доверенным входом**: при применении он валидируется
  заново Pydantic-черновиками (`services/drafts.py`), лимиты длины полей
  соблюдаются (`services/operations.py`). Даже если бы payload был подменён в
  БД, применить произвольную операцию нельзя — apply принимает только известные
  `PendingOpType` и типизированные поля.
- Ошибка применения (`OperationError`) переводит операцию в `failed` и пишется
  в audit; неожиданная ошибка откатывает транзакцию целиком, операция остаётся
  `pending` и может быть повторена безопасно.
- Секреты: значение шифруется **до** создания pending-операции; в payload
  лежит только шифротекст (`encrypted_value_b64`), открытый текст в БД не
  попадает (`conversation/engine.py`, `services/secrets.py`).

## 4. Криптография

Реализация — `src/jarvis/security/crypto.py`, AES-256-GCM (`cryptography`, AESGCM).

**Формат блоба**:

```
magic "JVSF" (4) | format_version (1) | key_version (4, big-endian) | nonce (12) | ciphertext||tag (16)
```

- Весь заголовок (magic, версия формата, версия ключа, nonce) передаётся как
  **AAD** при шифровании и расшифровке. Это значит, что любая правка заголовка
  ломает проверку тега GCM — расшифровать «переклеенный» блоб нельзя.
- **Почему нельзя подменить `key_version`**: расшифровка берёт ключ по версии из
  заголовка, а сам заголовок аутентифицирован. Подмена версии на существующую
  даст неверный ключ и `InvalidTag` → `DecryptionError`; на несуществующую —
  `UnknownKeyVersion`. Ошибка расшифровки неотличима от повреждения файла
  («wrong key or corrupted data»), детали наружу не раскрываются.
- Ключ — 32 случайных байта (`os.urandom`), в env — url-safe base64
  (`decode_key` проверяет декодирование и длину 32).

**Keyring и ротация**:

- `DOCUMENT_ENCRYPTION_KEY` + `DOCUMENT_ENCRYPTION_KEY_VERSION` — активный ключ,
  он шифрует новые данные; `DOCUMENT_ENCRYPTION_OLD_KEYS` — старые ключи
  (формат `1:<base64>,2:<base64>`), используются только для расшифровки.
- Ротация: сгенерировать новый ключ, увеличить версию, старый добавить в
  `OLD_KEYS`. Старые блобы продолжают читаться, новые пишутся новым ключом.
- Перешифровка данных — `scripts/reencrypt.py` (dry-run по умолчанию,
  `--apply` — выполнить; перешифровывает файлы хранилища и значения секретов,
  обновляет версии в БД, не печатает ключи). После успешной перешифровки старый
  ключ можно удалить из `OLD_KEYS`; до этого удаление ключа делает записи
  нечитаемыми безвозвратно.
- Секреты используют отдельный `SECRETS_ENCRYPTION_KEY` (если пуст — fallback на
  документный ключ). Отдельный ключ позволяет не смешивать домены: утечка одного
  ключа не открывает второй домен.
- В БД хранятся только версии ключей (`secrets.key_version`,
  `documents.encryption_version`), самих ключей там нет.

**Где живёт мастер-ключ**: только в `.env` на сервере (и в памяти процесса).
`.env` исключён из git (`.gitignore`) и из образа (`.dockerignore`), в БД и в
Docker-образ не копируется. Резервная копия ключей — обязанность владельца:
без ключа зашифрованные файлы и секреты не восстанавливаются.

## 5. Секреты

- Отдельная таблица `secrets`; значение хранится как зашифрованный blob
  (`encrypted_value`, `key_version`). Ни открытого текста, ни хешей значения в БД нет.
- Значение **не попадает**:
  - в поиск — `SearchService` ищет по `knowledge_items`, `tasks` и заголовкам
    документов; таблица секретов не участвует (`services/search.py`),
    в списках секретов показываются только имена;
  - в AI — контекст интерпретации ограничен временем, таймзоной, именами
    категорий/проектов и черновиком операции (`ai/provider.py`);
  - в MCP — проектно секреты не отдаются вообще (см. `docs/architecture.md`, раздел 7);
  - в логи — плюс общая редакция логов (раздел 8).
- Попытка сохранить секрет как обычную заметку блокируется по умолчанию: движок
  отклоняет черновик с подсказкой `secret` или признаками пароля/токена/ключа и
  предлагает команду `/secret` (`conversation/engine.py`).
- **Осознанный обход**: у отклонённого сообщения есть кнопка «Всё равно
  сохранить как заметку» — операция всё равно проходит через подтверждение, а
  сохранённая запись помечается уровнем `sensitive` (видна владельцу в поиске,
  не отдаётся MCP по умолчанию). Текст в базе остаётся открытым — кнопка
  предназначена для личного чата владельца (`bot/handlers/menu.py`,
  `menu_force_save`).
- Порядок сохранения: значение шифруется сразу при получении (до имени секрета),
  в состояние диалога и payload операции попадает только base64 шифротекста.
- **Показ значения** — отдельный явный сценарий: карточка секрета не содержит
  значения, кнопка «Показать» отправляет его отдельным сообщением и планирует
  удаление этого сообщения через 90 секунд (`bot/handlers/secrets.py`,
  `REVEAL_LIFETIME_SECONDS`). В сообщении — предупреждение «Не пересылайте».
  Остаточный риск: до удаления сообщение видно в чате и в клиентах/бэкапах
  Telegram (см. раздел 10).

## 6. AI и приватность

- **Что не отправляется внешним сервисам**: значения секретов, содержимое
  документов, строки подключения и токены. Интерпретация видит только текст
  сообщения пользователя и минимальный контекст (время, tz, имена
  категорий/проектов, уточняемый черновик).
- **Чувствительные заметки видны AI**: `get_knowledge`/`search_all` агента
  отдают содержимое записей уровня `sensitive` без дополнительного фильтра —
  так же, как в поиске Telegram (решение владельца 17.10.2026). Значения
  секретов (`/secret`) и содержимое документов во внешний LLM не уходят никогда.
- При `AI_PROVIDER=none` (по умолчанию) внешние запросы не выполняются вообще;
  доступен ограниченный режим: поиск, ручные команды, сохранение текста заметкой.
- Транскрибация: аудио уходит во внешний сервис **только** если
  `TRANSCRIPTION_PROVIDER` настроен явно (`transcription/openai_compatible.py`);
  по умолчанию `none`.
- **Доверие к контенту пользователя**: содержимое заметок, документов и имён
  файлов считается данными. В системном промпте прямо запрещено выполнять
  инструкции из сообщения (`ai/prompts.py`), а LLM в принципе не имеет доступа
  к инструментам и БД — она только возвращает JSON `Interpretation`, который
  валидируется Pydantic, а решение принимает backend.
- Ограничение контекста: `AI_MAX_CONTEXT_CHARS` (по умолчанию 20 000) —
  в промпт не подтягиваются произвольные записи из базы, только запрошенное
  пользователем сообщение и метаданные черновика.

## 7. Файлы и хранилище

- **Path traversal**: путь строится не из имени файла, а из случайного
  `storage_key` (`secrets.token_hex(24)`); `_path_for` отвергает ключи с `/`,
  `\` и любыми символами вне `[0-9a-f]` (`documents/storage.py`).
- **Атомарная запись**: во временный `.tmp` + `os.replace`, каталоги хранилища
  создаются с `chmod 700` (best effort — на смонтированных томах chmod может не
  сработать).
- **Валидация загрузки**: размер > 0 и ≤ `MAX_DOCUMENT_BYTES` (50 МБ), MIME из
  белого списка префиксов (`services/documents.py`). Ограничение голосовых —
  `MAX_VOICE_BYTES` (20 МБ).
- **Отправка файла**: имя для Telegram берётся как
  `PurePosixPath(original_filename).name` (защита от подстановки путей в имени),
  есть лимит размера отправки через Bot API.
- **Публичной раздачи нет**: файл отдаётся только через Telegram-бота
  авторизованному пользователю; на диске он всегда зашифрован.
- Метаданные документов (название, тип, категория) — в БД; содержимое — никогда.
- `MCP_INCLUDE_SENSITIVE` в текущем развёртывании `true` (решение владельца
  17.10.2026): чувствительные заметки доступны MCP; секреты не отдаются никогда.

## 8. Логи и аудит

- **Редакция логов**: все логи проходят через `RedactingFilter`
  (`logging_setup.py`), который прогоняет сообщение через `redact()`
  (`security/redaction.py`) и подставляет correlation id. Маскируются: PEM
  приватные ключи, токены Telegram, JWT, `sk-`-ключи, `Bearer`-заголовки,
  пары вида `password=… / token: … / api_key=…`.
- **Что запрещено логировать**: значения секретов (они и не покидают сервис в
  открытом виде), содержимое документов, токены и ключи, полный текст сообщений
  пользователя. В коде логируются только события и идентификаторы
  (`update_id`, `user_id` при отказе в доступе, ошибки провайдеров без тела запроса).
- **audit_log** (`repositories/audit.py`) пишет значимые действия:
  `actor` (`telegram:<id>`), `action` (`confirm:<тип операции>`, `cancel`),
  `entity_type`/`entity_id`, `result` (`ok`/`failed`) и `meta` — только
  нечувствительные данные (например, текст доменной ошибки). Payload операций,
  значения секретов и содержимое документов в audit не попадают.
- Запись audit идёт в той же транзакции, что и изменение сущности: откат
  транзакции не оставляет лживых записей об успехе.

## 9. Fail-closed поведение

- Пустой allow-list = запрет всем; в prod бот вообще не стартует без
  токена/allow-list/ключа шифрования.
- Нет ключа шифрования — загрузка документов и секретов недоступна
  (воркер уборки просто пропускает файловую часть).
- Ошибка AI — деградация к ограниченному режиму, а не обход подтверждений.
- Ошибка расшифровки/несовпадение SHA-256 — файл не отдаётся.
- Неизвестный тип операции, отсутствующий ключ для версии блоба, некорректный
  UUID — операция отклоняется, состояние не меняется.

## 10. Остаточные риски и что сознательно не защищено в MVP

Честный список:

1. **Компрометация сервера/процесса** — атакующий с доступом к процессу читает
   env с мастер-ключами и получает всё. Защита в MVP — только зашифрованные
   тома на диске.
2. **Компрометация Telegram-аккаунта владельца** — даёт полный доступ к боту
   (живой сеанс). Внешние меры: 2FA, завершение сессий, отдельный аккаунт.
3. **Telegram как канал хранения** — история чата, бэкапы Telegram и кэш клиентов
   содержат отправленные значения (в т.ч. «показ секрета 90 секунд»); это
   сознательный трейд-офф «телефон = интерфейс».
4. **БД не шифруется at-rest**: заметки, задачи, названия документов и секретов
   лежат в PostgreSQL в открытом виде (шифруется только значение секрета и
   содержимое файлов). Защита данных в БД — на уровне доступа к хосту.
5. **Резервные копии** — утечка бэкапа .env или дампа БД равносильна компрометации;
   шифрование бэкапов — на владельце (см. `docs/backup-restore.md`).
6. **Ротация ключей требует ручного запуска** `scripts/reencrypt.py --apply` на
   сервере (dry-run по умолчанию); до её завершения старый ключ обязан
   оставаться в `OLD_KEYS`.
7. **Нет антивирусной проверки файлов** — документ валидируется только по
   размеру и MIME; открывать его следует осознанно.
8. **Нет rate limiting и защиты от флуда** — посторонний не пройдёт allow-list,
   но владелец или утёкший токен не ограничены по частоте запросов (внешний
   риск — лимиты Telegram и кошелёк AI-провайдера).
9. **Удаление файлов — unlink без безопасного стирания**; на SSD копии могут
   оставаться на уровне носителя.
10. **MCP-модуль ещё не в сборке** — его поверхность атаки будет оценена после
    появления кода; уже сейчас зафиксировано: токен обязателен, порт только
    loopback, секреты и чувствительные данные не отдаются по умолчанию.
