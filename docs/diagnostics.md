# Диагностика и improvement backlog

Stage 2 Jarvis: система сама замечает свои сбои и трения, хранит их как
отдельные сущности и отдаёт владельцу на разбор вместе с диагностическим
контекстом. Передача в coding-агент — вручную, файлами.

## Модель данных

Две таблицы (миграция `19d82c1a6e02`):

**`improvement_items`** — одна запись на проблему/идею:

| Поле | Смысл |
|---|---|
| `category` | `failure` · `missing_capability` · `ux_friction` · `improvement_idea` |
| `source` | `technical_event` (подтверждённый сбой) · `user_observation` · `llm_hypothesis` |
| `confidence` | достоверность гипотезы (0..1), для сбоев — NULL |
| `status` | `new` → `reviewed` → `planned` → `implemented` / `wont_fix` / `archived` |
| `occurrence_count` | сколько раз наблюдалось (первый случай = 1) |
| `first_seen_at` / `last_seen_at` | временные границы наблюдений |
| `correlation_id` | id апдейта из логов (связать с журналом) |
| `component` | откуда пришло (`telegram_bot`, ...) |
| `diagnostic_context` | redacted: `error_type`, `traceback` (обрезан), метаданные апдейта |
| `title` / `summary` / `expected_behavior` / `actual_behavior` / `facts` / `assumptions` / `proposed_fix` | описание и разбор |
| `source_event_ids`, `merged_from`, `meta` | свидетельства, происхождение, служебные данные |

**`improvement_events`** — каждый отдельный случай: `item_id`, `occurred_at`,
`correlation_id`, `note`, `diagnostic_context`. Повтор проблемы не создаёт
дубликат записи: добавляется событие, растёт `occurrence_count`.

Дедупликация: открытая запись (`new`/`reviewed`/`planned`) с тем же
источником + компонентом + заголовком (без учёта регистра) считается повтором.
Объединение похожих записей: `ImprovementService.merge` — события переезжают
к целевой записи, источник архивируется с `meta.merged_into`, а его id
остаётся в `merged_from` (исходные свидетельства не теряются).

## Как записи попадают в backlog

1. **Технические сбои** — автоматически: обработчик `dp.errors` в `bot/app.py`
   вызывает `ImprovementService.record_failure` с типом ошибки, traceback
   (обрезается `IMPROVEMENT_CONTEXT_MAX_CHARS`), correlation_id и типом апдейта.
   Тела сообщений пользователя не сохраняются.
2. **Гипотезы LLM** — из разбора сообщений: модель может вернуть
   `improvement_hypothesis` (категория, заголовок, суть, evidence, confidence).
   Backend сохраняет её только при `confidence >= IMPROVEMENT_HYPOTHESIS_MIN_CONFIDENCE`
   (по умолчанию 0.75) — шум и домыслы в backlog не попадают. Ошибка записи
   не ломает диалог.
3. **`user_observation`** — зарезервировано для ручных наблюдений владельца
   (в интерфейсе пока нет отдельной кнопки; статус ставится через карточку).

Ограничение: при недоступной БД запись невозможна (сбой только логируется).
Локальный файловый буфер — вне текущей версии; см. «Ограничения».

## `/diagnostics` (алиас: `/status`)

Сводка: состояние БД, счётчики записей, AI/транскрибация/часовой пояс,
шифрование — плюс счётчики backlog по статусам и категориям.

Действия кнопками: «Открытые» и «Все»; раздельно по статусам и категориям;
пагинация по 7 записей; карточка записи со сменами статуса («Разобран»,
«В план», «Реализовано», «Не чинить», «В архив») и удаление — только после
отдельного подтверждения (hard delete вместе с историей событий).

## `/export_issues` — передача в OpenCode

```
/export_issues [status=new,reviewed,...|all] [category=failure|missing_capability|ux_friction|improvement_idea]
```

Без фильтров выгружаются открытые записи. Итог — два файла:

- `jarvis_issues_<timestamp>.md` — читаемая выгрузка по записям и событиям;
- `jarvis_issues_<timestamp>.json` — те же данные машинно (плюс `events`).

Файлы складываются в `EXPORT_DIR` (по умолчанию `var/exports/`) и отправляются
документами в Telegram. Лимиты: до 500 записей, до 4000 символов на строковое
поле. Секреты маскируются повторно (`security/redaction.py`) — при записи
и при экспорте.

OpenCode **не подключается к production-БД**: владелец передаёт файлы вручную,
агент читает их и работает по циклу из `AGENTS.md`.

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `IMPROVEMENT_HYPOTHESIS_MIN_CONFIDENCE` | `0.75` | порог достоверности гипотез LLM |
| `IMPROVEMENT_CONTEXT_MAX_CHARS` | `4000` | лимит traceback/контекста в записи |
| `EXPORT_DIR` | `var/exports` | каталог выгрузок |

## Ограничения

- Пока нет команды для объединения дубликатов из бота (сервис `merge` есть,
  UI для него — позже).
- Нет автоматической доставки исправлений обратно: статусы в боте — ручной
  шаг владельца (цикл в `AGENTS.md`).
- При недоступной БД события не буферизуются на диск (осознанно: диагностика
  не должна создавать теневых хранилищ данных); сбой остаётся в логах.
- `diagnostic_context` хранит traceback с именами переменных окружения, но
  значения ключей вычищаются redaction'ом; полные тела исключений всё равно
  не предназначены для публикации.
