# Резервное копирование и восстановление Jarvis

Скрипты: `scripts/backup.sh`, `scripts/verify_backup.sh`, `scripts/restore.sh`.
Все команды выполняются на сервере (Linux) из корня репозитория; скрипты рассчитаны на `docker compose` v2.

## Что попадает в резервную копию

`scripts/backup.sh` создаёт каталог `backups/jarvis-backup-YYYYmmdd-HHMMSS/` (каталог настраивается через `BACKUP_DIR`):

| Файл | Что это и почему |
| --- | --- |
| `pg.dump` | Полный дамп PostgreSQL в custom-формате (`pg_dump -Fc`, сжатый). Вся «память» Jarvis: документы/метаданные, задачи, знания, категории, история, `alembic_version`. Дамп снимается согласованно (снапшот MVCC), поэтому БД внутри себя консистентна. |
| `files.tar.gz` | Архив тома `jarvis-files` — это и есть содержимое `DOCUMENT_STORAGE_PATH` (`/data/documents` в контейнерах). Файлы лежат на диске зашифрованными (AES-256-GCM), приложение читает их через storage_key из БД. |
| `env.sanitized` | Копия `.env` **с маскировкой**: значения переменных, в имени которых есть `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, а также `DATABASE_URL`, заменены на `<removed>`. Нужна, чтобы помнить конфигурацию (провайдеры, лимиты, порты), не таща секреты. |
| `SHA256SUMS` | Контрольные суммы артефактов, проверяются `scripts/verify_backup.sh`. |
| `manifest.txt` | Дата, хост, версия Jarvis (`git rev-parse --short HEAD`, иначе `unknown`), состав копии. |

Что **не** бэкапится и почему: сами секреты (ключи шифрования, токены) — они обязаны храниться отдельно от копий данных; docker-образы и код — восстанавливаются из репозитория; том `jarvis-pgdata` — вместо него достаточно дампа, снятого согласованно.

Копии создаются с `umask 077` (доступ только владельцу). Старые копии старше `BACKUP_RETENTION_DAYS` (по умолчанию 14 дней) удаляются автоматически — только каталоги по маске `jarvis-backup-*`.

## Согласованность: важное окно рассогласования

`pg.dump` и `files.tar.gz` снимаются в разные моменты времени, и приложение между этими шагами продолжает работать. Поэтому:

- документ, добавленный **в момент** копирования, может попасть в дамп (запись в БД есть), но не попасть в архив файлов — после восстановления запись «висит» без содержимого;
- может быть наоборот: файл попал в архив, но записи в дампе нет — «осиротевший» блоб, который приложению не виден (он просто занимает место).

Для строгой согласованности останавливайте приложение на время копии:

```bash
docker compose stop app mcp
scripts/backup.sh
docker compose start app mcp
```

Простой бота безопасен: Telegram хранит недоставленные апдейты и бот заберёт их после старта. Для «почти согласованной» копии без простоя помните про описанное окно.

## Регулярный бэкап (пример cron)

```bash
# ежедневно в 03:30; замените <путь к репо> на реальный
30 3 * * * cd <путь к репо> && ./scripts/backup.sh >> <путь к логам>/jarvis-backup.log 2>&1
```

Проверяйте, что копии действительно появляются и не растут/не падают аномально. Каталог с копиями либо держите вне репозитория (`BACKUP_DIR=/var/backups/jarvis ./scripts/backup.sh`), либо добавьте `backups/` в `.gitignore` — в git копиям попадать нельзя.

## Проверка копии

```bash
scripts/verify_backup.sh backups/jarvis-backup-20260101-030000
```

Скрипт проверяет наличие всех артефактов, совпадение `sha256sum -c SHA256SUMS`, заголовок `PGDMP` у дампа и что в `env.sanitized` не осталось незамаскированных секретов. Он **не** проверяет, что данные реально расшифровываются и БД поднимается, — для этого нужно тестовое восстановление.

Рекомендуемый порядок: `verify_backup.sh` сразу после каждого бэкапа (можно дописать в cron) + тестовое восстановление раз в месяц/квартал, обязательно после обновлений схемы (миграций) и смены ключей шифрования.

## Восстановление в тестовое окружение

`scripts/restore.sh` восстанавливает копию в отдельное тестовое окружение и **никогда не трогает основной проект** `jarvis`: он не вызывает `docker compose` для основного проекта, а из `.env` только читает имена/пароль БД, не печатая их.

```bash
# 1) копия проверяется автоматически самим restore.sh
scripts/restore.sh backups/jarvis-backup-20260101-030000
# при необходимости — своё имя тестового окружения:
scripts/restore.sh backups/jarvis-backup-20260101-030000 --project-name jarvis-restore-test2
```

Что делает скрипт:

1. убеждается, что копия цела, а имя проекта свободно (иначе останавливается с ошибкой);
2. создаёт тома `<имя>_pgdata`, `<имя>_files` и сеть `<имя>-net`;
3. распаковывает `files.tar.gz` в том файлов;
4. поднимает `postgres:17-alpine` с теми же `POSTGRES_USER/POSTGRES_PASSWORD/POSTGRES_DB` и ждёт готовности;
5. заливает дамп через `pg_restore --no-owner`;
6. печатает следующий шаг: как запустить `app` против тестовой БД.

### Проверка, что восстановление сработало

```bash
# тестовый env: копия .env, в которой DATABASE_URL указывает на <имя>-postgres,
# а TELEGRAM_BOT_TOKEN (и внешние AI-провайдеры) можно отключить
docker run --rm --name jarvis-restore-test-app --network jarvis-restore-test-net \
  -p 127.0.0.1:8081:8080 \
  --env-file <тестовый .env> \
  -e DOCUMENT_STORAGE_PATH=/data/documents -e HEALTH_HOST=0.0.0.0 \
  -v jarvis-restore-test_files:/data/documents jarvis-app:local
```

1. **Health**: `curl -s http://127.0.0.1:8081/healthz` — ожидается HTTP 200 и `"status":"ok"` (внутри проверяется подключение к БД). Миграции применяются автоматически при старте контейнера.
2. **Данные**: посмотрите список документов/задач (через бота или MCP), поищите пару записей, убедитесь, что категории/связи на месте. Число документов в БД должно быть близко к боевому.
3. **Расшифровка файла** — главная проверка связки «БД + том + ключ»:

```bash
docker exec -i jarvis-restore-test-app python - <<'PY'
from pathlib import Path
from jarvis.config.settings import get_settings
from jarvis.security.crypto import decrypt

settings = get_settings()
root = Path(settings.document_storage_path)
files = sorted(root.glob("*/*.bin"))
if not files:
    raise SystemExit("файлов нет — том восстановлен пустым или ключ/путь неверны")
blob = files[0].read_bytes()
data = decrypt(blob, settings.document_keyring())
print("OK:", files[0].name, len(data), "байт, начало:", data[:60])
PY
```

Если расшифровка не удалась — в тестовом env не тот `DOCUMENT_ENCRYPTION_KEY` (см. ниже) либо файл в архиве повреждён.

После проверки тестовое окружение удаляют:

```bash
docker rm -f jarvis-restore-test-app jarvis-restore-test-postgres
docker volume rm jarvis-restore-test_pgdata jarvis-restore-test_files
docker network rm jarvis-restore-test-net
```

### Реальное восстановление (кратко, осторожно)

Для боевого восстановления: остановите `app` и `mcp`, восстановите дамп в основную БД (в пустую базу; удобнее всего тем же `restore.sh`-порядком команд через `docker compose exec -T postgres pg_restore ... < pg.dump`), верните файлы в том `jarvis-files` (`docker run --rm -v jarvis-files:/data -v <копия>:/backup:ro alpine tar -xzf /backup/files.tar.gz -C /data`) и запустите сервисы. Перед этим обязательно сделайте свежую копию текущего состояния: боевое восстановление затирает данные.

## Ключи шифрования — храните отдельно

Файлы в томе и часть полей в БД зашифрованы мастер-ключами `DOCUMENT_ENCRYPTION_KEY` и `SECRETS_ENCRYPTION_KEY` (а также ключами предыдущих версий `DOCUMENT_ENCRYPTION_OLD_KEYS`). Эти ключи есть только в `.env` на сервере.

- В резервные копии ключи **не попадают** (`env.sanitized` их маскирует) — это сделано намеренно.
- Без `DOCUMENT_ENCRYPTION_KEY` файлы из `files.tar.gz` восстановить **невозможно**: это не вопрос скрипта, шифротекст без ключа бесполезен.
- Без `SECRETS_ENCRYPTION_KEY` не расшифруются сохранённые секреты сервисов (если отдельный ключ не задан, используется `DOCUMENT_ENCRYPTION_KEY`).
- Держите копию ключей в менеджере паролей или сейфе — **не в каталоге резервных копий**, не на том же диске/сервере и не в git. Скомпрометированный бэкап вместе с ключом = доступ ко всем данным.
- При ротации ключа сохраняйте старые значения в `DOCUMENT_ENCRYPTION_OLD_KEYS` и их бэкапы — иначе файлы, зашифрованные старыми версиями, перестанут читаться.

## Ограничения скриптов

- `backup.sh` не останавливает приложение (см. «окно рассогласования»), не шифрует копии и не проверяет свободное место на диске. Хотите шифровать копии на диске или перед отправкой offsite — делайте это сами (`gpg`/`age`, шифрованный диск).
- SHA256 защищает от порчи, но не от подмены копии злоумышленником с доступом к серверу.
- Ротация удаляет каталоги старше `BACKUP_RETENTION_DAYS` без дополнительного подтверждения. Копии, которые нужно сохранить дольше, выносите из `BACKUP_DIR`.
- `restore.sh` восстанавливает **только** в тестовое окружение; параметры БД он читает простым парсером `.env` (сложные кавычки/экранирование могут разойтись с тем, как `.env` понимает `docker compose`).
- `verify_backup.sh` не поднимает базу и не читает файлы — полную проверку даёт только тестовое восстановление.
- Скрипты рассчитаны на Linux-хост (пути монтируются в контейнеры как есть). Запуск из Git Bash на Windows не гарантируется.
- Метаданные, которые писались в БД в момент копии, и незавершённые операции могут отражать состояние «на момент снимка» — это ожидаемо.
- Тренируйтесь: непроверенная резервная копия — это не резервная копия. Минимум раз в квартал (и после обновлений) прогоняйте `restore.sh` и шаги проверки выше.
